# Fork/import integrity repair

The original probe (`planning-transfer-probe.json`) reproduced three successful transfers whose active revision failed `StateCommitManager.verifySnapshot`. It remains unchanged as the failing baseline.

The repair stages each copy independently and verifies its exact current pointer before Engine recovery can choose an older revision. Identity/name changes use the existing Core `StateCommitManager.commit` boundary with the expected source revision and all canonical state slices. Old revisions are preserved byte-for-byte; this transfer commit does not apply default historical pruning. The current project wrappers and document manifest carry the new identity, with source project ID/revision recorded in `forkedFrom`.

Copied runtime files move unchanged to `history/transfers/<id>/runtime`. A transfer index records the source identity/revision and archive mapping. PlanningRuntime cannot list/resume those old runs. Approved blueprint blocks and approval history remain; unapproved proposals become stale for the new identity. Old development packages remain in artifacts, but the new identity has no current package reference. Same-ID/no-collision import preserves its original metadata bytes and revision, with execution history isolated.

The genuine-tree regression also found that export had omitted every hidden `.agents` worker directory. Export now retains hidden tool traces and worker configuration; only Core's transient commit staging/marker entries are excluded. Import rejects malformed ZIP directories, inconsistent headers, CRC/size mismatches, path traversal and duplicate file entries before promotion.

Validation used only independent temporary copies of frozen `flash-materials-quality-20261005-01/project-records` (revision 21, 30 blueprint blocks). The three changed-identity paths produce valid revision 22; same-ID round trip remains valid revision 21. Tests compare every old revision file, material file, artifact/package file and runtime file by SHA-256, including hidden worker evidence. They compare the entire source and existing destination tree before/after; those trees are unchanged.

The targeted run passed 10 tests in 3 files. It covers all four transfer paths, genuine history/material/approval preservation, runtime isolation and new run creation, readiness/document history, foreign-package invalidation, corrupt current snapshots with valid predecessors, injected Core write failures, collision safety and malformed archive cleanup. Core TypeScript no-emit checking also passed after the coordinated contracts build. No live Provider call was made for this repair.

Machine-readable evidence is saved in `planning-transfer-integrity-vitest.json` and `planning-transfer-integrity-2026-10-05.json`. This is transfer-integrity evidence, not model semantic acceptance or target-project implementation acceptance. No changes were committed.

Independent review added two export regressions: concurrent Core commit during archive reads could mix revisions, and a project junction could cause the exporter to read outside the project tree. The corrected probe failed both cases (`project-export-consistency-red2.txt`); export now normalizes the root path, holds the shared Core lock during all archive reads and rejects project symlinks/junctions before reading their content. The transfer/export suite then passed 12 tests in 3 files (`project-export-transfer-green.txt`). This Core lock does not freeze live Runtime progress logs; copied execution observations remain isolated history and cannot resume in the transferred project.

The subsequent public-entry review found a separate bypass: duplicate called `engine.getSnapshot` to obtain its default name, and canonical registry discovery called `engine.loadProject` before duplicate/export reached the transfer service. A corrupt current revision could therefore be silently recovered to a valid predecessor, changing source bytes and deleting the corrupt revision. Both transfer routes now call `resolveProjectLocationReadOnly(rawId: string): Promise<string>` in the `createApp` closure. This helper validates the ID, workspace containment, existence and recycle-bin exclusion; it returns either the registered location or canonical location without loading/recovering state or writing registry entries. It intentionally does not prove snapshot validity: each transfer operation validates its exact source under the shared Core lock. Future read-only diagnostics may reuse this interface without routing through the recovery resolver.

An omitted fork name is now derived inside `ProjectForkService` from the copied, frozen and verified snapshot metadata. The HTTP route no longer loads the source to choose a name and registers the actual returned fork name. Explicit names still use the existing validation. Export verifies the exact current pointer before reading archive payloads; a corrupt current revision now fails with `STATE_VALIDATION_FAILED` rather than returning a backup of silently recovered state. The import-corruption regression uses a valid exported bundle whose snapshot payload is deliberately corrupted and repackaged with a correct ZIP CRC, so it still proves snapshot-hash rejection independently of export's new refusal.

Classic ZIP layout is validated before payload checksum scans, header writes and final buffer allocation. Export first validates file-stat sizes, and the builder repeats validation against the actual bytes read because live Runtime observations can change between those reads. Validation covers entry counts above 65535, file names outside 1–65535 UTF-8 bytes, individual file sizes and accumulated local-record/central-directory fields beyond 32 bits, plus the current Node buffer capacity. Unsupported layouts fail explicitly; no ZIP64 archive is generated. These are representation limits of this archive format, not limits on Provider calls, planning history or revision rounds. Valid boundary controls preserve 65535 entries and exactly 65535 UTF-8 name bytes.

The new red run (`project-transfer-entry-boundaries-red.txt`) recorded 12 failures and 3 passes before implementation: four registered/unregistered corrupt-current HTTP cases incorrectly returned success, two healthy-source cases changed raw source bytes, the omitted fork name was rejected, two ZIP builders returned overflowed archives, and three numeric layout checks had no implementation. Positive ZIP boundary and checksum-preflight controls were added afterward. The final transfer suite passed 29 tests in five files (`project-transfer-entry-boundaries-green.txt`), including the six HTTP cases, all four genuine frozen-copy transfer paths, failure cleanup, unchanged source/history hashes, hidden-record preservation, link rejection and concurrent formal-commit exclusion. The existing explicitly named HTTP fork lifecycle also passed (`project-transfer-explicit-name-lifecycle-green.txt`; only its P1-1 case was selected, with three unrelated cases excluded).

Source-alias TypeScript checking reported zero diagnostics without emitting files or running a build (`project-transfer-entry-boundaries-typecheck.txt`). Three existing fork fixtures used the obsolete `projectName` input key; they now use the actual `name` contract. No live Provider call, build, commit, or edit to frozen real evidence was made.
