# Project Architect V1：产品边界与架构原则

> 文档状态：Phase 1.1 Blueprint  
> 范围：产品使命、V1 边界、行为约束与职责划分。  
> 非范围：具体实现方案、界面视觉设计与开发任务细化。

## 1. 产品使命

Project Architect 是本地运行的 AI 项目规划工作台。它帮助个人开发者在开始 AI Coding 之前，把模糊想法逐步转化为明确、可审阅、可交给 Coding Agent 的开发蓝图。

它服务的不是“尽快生成代码”，而是“先把正确的项目想清楚”。系统应帮助用户明确目标、用户、问题、MVP 边界、核心流程、体验方向与关键约束，再生成开发文档。

```text
Idea → Clarification → Project Understanding → Development Blueprint → Coding Agent Input
```

## 2. 核心价值

- **减少错误开工。** 在编码前暴露缺失决策、范围膨胀、风险与真实冲突。
- **保留用户主导权。** AI 可以挑战和推荐，但不能把推断悄悄变成用户确认的事实。
- **把探索变成可用资产。** 对话中的有效结论沉淀为结构化 Overview、决策状态和 Markdown 文档。
- **以最少打扰推动项目。** 只问当前最值得用户回答的问题；低风险、可逆的默认项显式记录为 Assumption。
- **为 AI Coding 提供可靠入口。** 输出的文档表达已确认的产品定义、范围、约束与未决风险，而不是伪装成完整实现设计。

## 3. 用户问题

V1 面向个人开发者和 AI Coding 使用者。他们通常遇到以下问题：

- 只有一句构思，不知道先澄清什么。
- 已有零散文档、图片或设计稿，但缺少统一的项目理解。
- 在需求尚未闭合时就开始编码，导致反复返工。
- 不知道哪些决定必须自己确认，哪些可暂时采用默认值。
- 需要把探索结果整理成 Coding Agent 可读取的开发输入。

Project Architect 不替用户决定项目方向；它使这些决定、推荐、假设与风险变得可见且可追溯。

## 4. 使用场景

### 从一句想法开始

用户输入一个模糊想法。系统先进行首次理解分析，展示已知信息、Candidate、未知信息和风险；首次分析不直接进入问答。随后系统在 Broad Pass 中识别高价值缺口，并按优先级引导澄清。

### 整理已有材料

用户提供文本、文件或图片等已有材料。系统把材料中的用户明确表达与 AI 推导内容分开，形成统一 Overview，并只继续追问真正缺失的关键决策。

### 收敛为开发蓝图

用户通过对话或直接编辑 Overview 完善项目。系统进行 Readiness Review，标明 Ready、Warnings、Issues 和 Assumptions；用户批准后生成 Markdown 开发文档。

## 5. V1 范围

V1 必须形成一个完整的“想法到开发文档”闭环：

1. 创建和保存本地项目。
2. 接收文本、文件和图片形式的项目输入。
3. 进行首次理解分析，明确区分 Confirmed、Candidate、Assumption、Unresolved 与 Warning。
4. 维护结构化 Project Overview：固定核心内容与按项目需要出现的专项内容。
5. 以 Gap-first 方式发现、排序并生成问题，避免固定问卷。
6. 支持用户通过对话或直接编辑更新项目状态；支持将已确认决定标为 Locked。
7. 在生成文档前执行 Readiness Review，并由用户最终批准。
8. 生成核心 Markdown 文档与按项目类型出现的专项文档，作为 Coding Agent 输入。
9. 使用已冻结的 B2.1 Agent 行为：单一专门 Agent、一次推理调用、结构化输出、产品优先于技术、严格 Conflict 分类。

V1 的结构化状态至少覆盖：项目概述、决策、Assumptions、Gaps、Readiness、对话历史和生成文档。Overview 是用户可读的项目窗口；它不应替代规范状态本身。

## 6. 明确不做事项

V1 不承担以下职责：

- 自动生成、修改或运行用户项目代码。
- 代替用户直接作出产品方向、目标用户、MVP、平台或其他高影响决定。
- 作为普通闲聊机器人或通用 PRD 写作工具。
- 多 Agent 协作、投票或持续互相审查。
- 企业协作、组织权限、完整需求追踪、Git 集成或自动部署。
- 对已有软件项目执行变更影响分析；该能力属于后续版本。
- 管理或监督 Coding Agent 的开发执行；该能力属于后续版本。

## 7. 核心设计原则

### 7.1 用户授权高于 AI 推断

只有用户明确陈述或批准的内容才能成为 Confirmed。AI 的建议、行业惯例和推断必须保持为 Candidate、Gap、Risk、Tension 或符合条件的 Assumption。用户始终可以修改自己的项目定义。

### 7.2 先定义产品，再讨论实现

Discovery 阶段优先澄清用户、问题、价值、工作流、MVP、平台偏好、数据与信任承诺、UX 方向和交付阶段。除非用户明确进入技术规划或技术约束阻塞可行性判断，AI 不主动引入具体实现机制。

### 7.3 Gap-first，而非问卷优先

系统先从当前 Project State、Checklist 与动态推理中识别 Gap，再结合 Impact、Uncertainty、Irreversibility、Dependency 与 Stage Relevance 排序，最后只生成最有价值的问题。

高影响或关键问题通常一次只问一个，并说明为什么现在问、推荐方向及其影响。普通问题只在主题紧密相关且不会打断用户思考时成组出现。低风险项应尽量不打扰用户。

### 7.4 分类必须精确

Conflict 仅表示两个已确认、已锁定或硬约束无法同时成立。风险、成本、复杂度、UX 取舍和范围过大分别属于 Risk、Tension 或 Scope Gap，不能借用 Conflict 标签放大问题。

### 7.5 推荐可见、假设可见、状态可审阅

AI 可以提出明确建议并解释原因，但推荐不是决定。任何 Assumption 都必须显式展示；任何状态改变都必须可由用户理解和修正。系统不得静默覆盖已有确认或锁定决定。

### 7.6 先本地处理，再调用 AI

状态保存、简单校验、去重、锁定检查、格式整理和文档装配应优先在本地完成。只有理解、推理、挑战、排序、推荐与创造性表达才需要 AI。

### 7.7 上下文最小化与单次推理

每次 AI 调用只接收当前任务所需的 Project State 与相关材料，不默认发送完整历史。一个用户动作对应一个清晰的推理任务，最多一次主要 Agent 调用；不得把逻辑分解成隐蔽的连续推理调用。

### 7.8 Readiness 是建议，不是越权阻止

Readiness Review 用于说明项目是否足以形成开发蓝图。系统优先给出 Warning 和影响说明；只有未解决的关键缺口或真实 Conflict 才应要求用户明确确认。最终继续与否由用户决定。

## 8. Agent 与 System 职责边界

| Agent（AI）负责 | System（程序）负责 |
| --- | --- |
| 理解输入材料，提取用户明确表达与不确定内容。 | 保存、读取、版本化并校验 Project State。 |
| 发现 Gap、Risk、Tension、Scope Issue 和真实 Conflict。 | 应用状态迁移，保留历史，阻止静默覆盖与无效状态。 |
| 对项目价值、MVP、核心流程、信任承诺和体验取舍进行挑战与推荐。 | 构建最小相关上下文，控制调用次数与上下文预算。 |
| 按优先级选择最值得问的问题，并提供产品级推荐。 | 去重、检查 Locked 决定、执行确定性规则与展示状态。 |
| 产生严格符合结构化契约的分析、问题、推荐和 Readiness 结论。 | 校验结构化输出，记录原始结果，将已批准内容编译为 Markdown。 |

Agent 只能提出状态更新建议，不能直接成为状态的最终权威。System 只执行确定性规则和用户已授权的变更，不替代 Agent 进行产品推理。

### 状态变更原则

```text
用户输入或直接编辑
  → System 写入可追溯的 Project State
  → System 选择最小相关上下文
  → Agent 返回结构化分析与建议更新
  → System 校验、展示并按授权更新状态
  → Overview / Readiness / Markdown 使用同一规范状态
```

当用户编辑内容与既有 Confirmed 或 Locked 决定不一致时，System 必须保留变更痕迹并提示影响；Agent 负责解释影响和提出下一步，不得自行决定覆盖哪一项。

## 9. 本阶段结论

Project Architect V1 的本质是一个由用户主导、由结构化状态支撑、由 AI 提供审慎挑战的项目定义工作台。它的成功标准不是产出更多文本，而是让用户在编码前获得更少歧义、更清楚范围和更可靠的开发输入。
