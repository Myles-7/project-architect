# B3 自适应多问题 Discovery

> 状态：生产运行时权威规范。本文取代旧蓝图中的 B2.1 Prompt、Schema 和单题预算描述；旧实验资产仅保留为历史证据。

## 1. 不变量

- 单 Agent；一次用户 Discovery 操作最多一次主要 Provider 调用。
- Provider 结果必须通过 `b3-discovery.schema.json`，状态更新不得解析自然语言文本。
- AI 只能产生建议；Confirmed/Locked 只能来自用户陈述、回答或手动编辑。
- 用户回答立即写入本地 Project State；后台建议绑定 revision，取消、失败和过期均零污染。
- Discovery 描述产品能力、边界和取舍，不提前决定实现机制。
- 用户可见的问题、理由、推荐、选项和影响默认使用自然简体中文；API、MVP、Windows 等必要专业名词可以保留。
- 每个问题只询问一个具体决策。选项影响必须说明选择后在范围、体验、时间、成本、工作量或风险上的实际变化，禁止只写“更好”“更灵活”“影响较大”等空泛结论。

## 2. 自适应问题预算

Core 根据 8 个核心 Overview 区域的 `mostly-clear` / `clear` / `locked` 数量决定阶段：

| 阶段 | 明确区域 | 目标 | 硬上限 |
| --- | ---: | ---: | ---: |
| `initial` | 0–2 | 8–12 | 12 |
| `explore` | 3–5 | 5–8 | 8 |
| `converge` | 6–8 | 2–4 | 4 |
| `readiness` | Readiness 及以后 | 仅阻塞问题 | 2 |

目标数量不是最低强制值。没有足够的有效决策时不得生成填充问题。

## 3. 独立问题集

每个 Gap 和 Question 必须包含稳定 `decision_key` 与 `depends_on`：

1. 已解决、已回答、Low-risk 和重复决策先被过滤。
2. `depends_on` 中存在未确认决策的问题延期到后续批次。
3. 同批 `decision_key` 唯一；回答一题不得改变同批其他题的题干、选项、推荐或语义。
4. Core 按 Critical/High、产品区域优先级和本地 `priorityScore` 排序，并执行硬上限。
5. Agent 字段缺失、未知依赖和依赖环只使相应问题失效，不阻止其他合法建议提交。
6. Core 还会校验中文可读性和选项影响是否具体；不合格的 Agent 题目不会直接展示，而会按关联 Gap 生成中文兜底题。

## 4. 交互与状态

- 每题“确认并继续”只走本地 `answerQuestion`，立即产生 Confirmed 决策和 trace。
- “立即推演”先保存回答，再启动可取消的后台 Discovery Job。
- 用户可批量 dismiss 未回答问题；dismiss 不创建决策。
- 当前批次回答或明确跳过后，用户才能生成下一批问题。
- B3 状态使用 `gaps.json` / `questions.json` schemaVersion 2；旧项目加载时内存迁移，下一次正常提交时持久化。

## 5. 发布质量与基准门槛 (Release Gates)

1. **自动契约门槛**：
   - 结构化输出成功率 100%。
   - 单操作 Provider 调用次数严格为 1 次。
   - 4 阶段问题预算越界 0 项。
   - 决策键重复 0 项；同批直接/间接依赖冲突 0 项。
   - 推荐 Option Key 不匹配 0 项；非中文/劣质文本 0 项。
   - Locked 架构决策越权覆盖 0 项；内部架构系统术语泄露 0 项。

2. **人工评审门槛**：
   - 每个 Case 由双人独立复核并记录两份带证据引用的真实评审意见。
   - 相关性、决策价值、独立可回答性、清晰度、选项影响有用性 5 个维度各自平均分均 ≥ 4.0/5.0，且任何单项评分不得低于 3.0。
   - 缺少评审证据时必须判定 `NOT READY`；禁止由 Runner、模型或固定模板代填评分。

3. **性能门槛**：
   - p50 耗时 ≤ 30s，p95 耗时 ≤ 60s。
   - Question 上下文严格限制在 12,000 字符以内。
